# Explaining ideograms

For EXPLAIN / RECOMMEND requests. SKILL.md §1 is usually enough; this adds the contrasts and
the reasons that make the form distinctive.

**What it is.** A well-defined statement of purpose plus optional context, packaged so whoever
receives it can talk to it, attempt a response, ask whether that response qualifies, and be
coached toward sufficiency. Any document with a purpose, a bar for having engaged with it, and a
way to self-check against that bar is an ideogram. Shapes: status request, capability handoff,
experiment capture, concept brief, design-intent brief, decision record (SKILL.md §2).

**How it differs from what people usually reach for.**
- A **ticket** states a task; an ideogram also states the purpose, the bar for done, the
  reasons, and how to self-verify.
- A **spec** is static and states a bar; an ideogram can be run conversationally and lets the
  reader grade themselves against the bar (I3 is what makes it not a spec).
- A **prompt** drives one model turn; an ideogram is durable, human-readable, addressed to
  people first and Claude second, and re-runnable as the work matures.
- A plain **document**, pasted into Claude, gets described back ("this file contains twelve
  decisions about…"). An ideogram's front door makes Claude *become* it instead (I0).

**What it does when run.** Works the task with the reader, evaluates a draft against its bar
and coaches the gaps (never gatekeeping), teaches the idea it carries, and helps the author
assemble what came back (SKILL.md §4).

**When one fits.** A document important enough that a vague version would waste a capable
reader's time, where the author would rather invest once in a precise, self-checking ask, brief
or record. Generic document creation ("capture my notes in a doc") is not a fit.

**Recommending.** Say whether one fits and why, offer to draft it, and wait for the go-ahead.
